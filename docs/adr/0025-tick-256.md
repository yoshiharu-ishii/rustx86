# 0025: tick粒度 64→256 (時間の換算は不変、まとめ幅だけ広げる)

日付: 2026-08-18 / 状態: 採用 (ユーザー裁定 2026-08-18「tick256でRTT再計測してJITは終わらせようか」) / 関係: [0024](0024-f1d-i-chaining.md)

## 背景

F1d-iの調査で、実行エンジンの「往復」の天井はtick粒度だと判明した
(予算 = min(鎖残り, tick_countdown))。粒度64では64命令ごとに必ず
清算・再入場の往復が入り、JIT・インタプリタ双方の上限を規定していた。

## 決定

- `INSTRUCTIONS_PER_TICK`: 64 → **256**
- `PIT_CLOCKS_PER_TICK`: 1 → **INSTRUCTIONS_PER_TICK / 64 (=4)**

後者が本体の半分である。**「1命令 ≒ 10ns」のゲスト時間換算は校正の原点
(64命令 = PIT 1クロック) のまま不変**で、変えるのは配送のまとめ幅だけ。
粒度だけ4倍にしてPITを1クロックのままにすると、ゲスト時計が命令比で
1/4に遅くなり、benchカーネルが起動途中でデッドハルトした (実際になった —
時間の換算とまとめ幅は別の量である)。

## 影響と検証 (2026-08-18)

- **決定的命令数は不変**: 換算を保ったので、凍結benchペアのブートは
  tick=64と同じ **970,000,000命令ちょうど** で着地する (定規は無傷)
- **シリアルFNVは変わる** (e841… → 8810…): dmesgのµsタイムスタンプが
  4クロック単位の配送ジッタで揺れるため。門番はon/off一致 (相対) なので
  基準の張り替えは不要 — 新値でもon/offビット同一
- **性能** (交互A/B): gcc窓 off ~78-80 vs on **~82-83 MIPS (JITが窓でも勝つ)**。
  起動+コンパイル全体 24.6-25.2 → **20.4-20.6s (-17%)**。
  jboot: on 7.3s = **133 MIPS**
- **RTT (netlat、wsslirpd折り返し)**: 悪化なし。刻み10Mで88.3→88.6ms (同)、
  1Mで37.4→**28.6ms (改善)**、100kで16.1→**10.2ms (改善)**、16bitは完全同一。
  RTTの主因はスライスの刻み (壁時計) であってtick粒度ではない — 換算を
  保てば揺らがない
- テスト204本全緑。ゲスト時間をハードコードしていた2本 (elks tetris
  tempo・zmiy) は「命令/PITクロックの比」で書き直した — 粒度を変えても
  比が契約
- 割り込み配送の粒度は64→256命令に粗くなる (ゲスト可視)。実OS 3種
  (ELKS/FreeDOS/Linux)・ゲーム・gcc・TLS・RTTの全実測で退行なし

## 棄却

- tick=128 (折衷): 256で実害が見つからなかったので不要
- さらに512以上: 収穫逓減が予想され、割り込みレイテンシの粗さだけが
  積み上がる。必要になったら実測とセットで再訪
