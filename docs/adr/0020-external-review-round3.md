## 背景

100 MIPS達成 (2026-08-13) とネットワーク・ディスクの一段落後、CPU最適化の
第3ラウンドとして外部レビュー (ChatGPT、コード読み・2往復) を受領した。

実測棄却済み) し、再審しない**。

今回は往復の中で外部レビュー側も台帳を読み直し、初回案の過半を自己撤回した。

## 境界チェックのイベント駆動化: 裁定の詳細

提案は「fault/trap/halted/IF/IRQの毎命令チェックを、境界状態を変え得るuopの後
だけにする」。**意味論の監査は通る**:

- chain内のuop語彙に trap/halted/IF/pic_service を変えるものは無い
  (HLT・STI/CLI・POPF/IRET・INT・IN/OUTは全部語彙外 = フォールバックで
  チェーン脱出)。exec.rs にこれらへの代入は存在しない
- chain内で境界状態が変わる源は正確に2つ: **F_MEM uopのフォールト**と、
  ループ末尾の **tick_devices が起こすIRQ**。つまり新ビットは不要で、
  既存F_MEM + 「前反復でtick発火」の1フラグで網が閉じる
- 罠: 現在の順序は exec→検査→tick。tick(N)のIRQは exec(N+1) の後に見える。
  tick直後に検査すると配送が1命令早まり**命令数ビット同一が壊れる** —
  実装するなら「tick後の検査は次のexecの後」の順序を守ること

**性能の前提は判別則(4)の読み違え**と裁く。検査群は独立ロード上の
predicted-not-taken分岐で、次反復の入力 (pa→slot→Entryロード→len→次pa) に
値を供給しない。制御依存はOoOが投機で突き抜ける — 直列化するのは
データフロー鎖だけ。同族の実測反証が既にある: batch2「境界検査の証明つき
省略」(PR #104) はワッシュで、台帳も「帳簿・照合・検査は既にOoOの影」と
記録済み。もし勝つとしたら機序はループ本体の痩身 (フロントエンド) で、
それはP2と同じ仮説に合流する。

## 判別則(4)の精密化 (今回の収穫)

> **削って効く「直列」とはループ搬送依存のこと** (PR #114) — に足す:
> **制御依存はデータ依存ではない。** 予測が当たり続ける分岐は、たとえ
> 「毎命令必ず通る」形でも鎖の辺ではない。真のループ搬送鎖は
> `pa → slot → Entryロード → len_flags → 次のpa` の**命令あたり依存ロード1本**
> であり、これはインタプリタの原理的な床に近い。

第3ラウンド以降の案は、ソースを眺めて「速そうな仕事」を探すのではなく、
この鎖グラフに対して「どの辺を短くするか」で出すこと。鎖に残る辺を崩す手
(デコード時に次スロットを焼く等) はトレースキャッシュの家系 (B5 +8%悪化) に
接近するので、着手前に家系の負け履歴と突き合わせること。

## Part 2の進め方

1. **P0: note_write配線の返済** (正しさ。本ADRと同時系列のPR)
   - 網に入れる: `write8`・`write_wide`・`fast_write8/16/32` (mem/mod.rs)、
     fast RMWの直書き4箇所 (dcache/exec.rs)
   - 網の外で良いもの: ブートローダ (実行開始前 = dcache空)・snapshot復元
     (dcacheを作り直す)・BIOS int13 (write8経由になる)・virtio-blk/REP文字列 (配線済み)
   - 手順: SMC再現テスト (修正前に赤) → 配線 → cargo test → 交互A/B 5周で
     書き込み側1判定の税がノイズ床 (±4%) 内であることを確認
2. **census batch** (opstats拡張のみ、判定はしない): 境界チェック成立の内訳
   (fault/trap/halted/irq別) と F_MEM比率、EA形の動的分布 (P4用)。
   台帳に数字を寝かせ、前提が変わったときの再訪材料にする
3. **P2: translate_for のhot/cold分離** (I-cache仮説と明示して、安い1発)

wasm (ブラウザ) 側は蛇口が全部閉じている (P3の項) ため、Part 2の対象外。
残る差はLLVMのwasmコード生成の税で、core不可侵下では触れない。

## 教訓

- **外部レビューは往復させると質が上がる**。初回案5本中3本は台帳の再審だったが、
  台帳を示して返したら自己撤回し、判別則(4)を踏まえた新提案を出し直してきた。
  レビューを裁く側の義務は「棄却」ではなく**負けた実測の履歴を渡すこと**
- **台帳が最強の防壁**。P1もP4も「もう裁かれた案」だと言えたのは、ワッシュや
  負けを理由つきで記録し続けた (ADR-0014の方法) おかげである
