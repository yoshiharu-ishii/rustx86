# ADR-0001: 16bit CPUから始め、Unicornをオラクルに検証する

- ステータス: 承認 (2026-08-07)
- 決定者: プロジェクト著者

## 背景

x86エミュレータを一から書く。最終的にはOSを動かしたいが、最初の壁は
**「自分のCPUが正しいと、どうやって知るか」**である。

ゲームボーイエミュレータではBlargg氏のテストROM群が事実上の標準で、これを流せば
CPUの正しさがほぼ担保できた。x86には同等のものが存在しない。しかもx86は検証が
難しい方向に尖っている。

- **命令が可変長** (1〜15バイト)。プレフィクスが任意個先頭に付く
- **フラグの意味論が複雑**。全ALU命令が CF/OF/SF/ZF/AF/PF を規則に従って更新する。
  特に AF (下位4bitからの桁上がり) と OF (符号付きオーバーフロー) は
  **境界値でしか姿を現さない**
- **歴史の地層**。リアルモード → プロテクトモード → ページング と、
  同じCPUが複数の人格を持つ

フラグが1ビットずれるバグは、OS起動中に条件分岐がひとつ曲がって初めて発覚する。
そこから原因の命令まで遡るのは現実的でない。**バグを作った瞬間に捕まえる**仕組みが
先に要る。

## 決定

### 1. リアルモード8086から始め、歴史の地層を順に登る

いきなり32bitや64bitを狙わない。x86は後方互換の積み重ねでできており、
下の層を飛ばすと上の層の意味が分からなくなる。リアルモードが動けば、
プロテクトモードは「同じ命令に別の解釈が乗る」として理解できる。

### 2. オペコードのグリッド構造をビットで畳む

x86のオペコードは一見でたらめだが、規則的な格子を持つ部分が大きい。
`0x00`〜`0x3D` は (演算種別3bit) × (形式3bit) の格子で、48命令が1ハンドラに畳める。
256行のテーブルを手で書かず、**規則的な部分は規則として書き、
歴史的な不規則部分だけ個別に実装する**。

### 3. レジスタは最初から `u32` で保持する

リアルモードでは16bitしか使わないが、32bit拡張が確定しているため最初から
`u32` で持ち、16bitビューで操作する。後から型を広げる改修は影響範囲が広い。

### 4. 未実装オペコードは即 panic する

黙って NOP として無視すると、遥か後方で意味不明な暴走として現れる。
オペコードと `CS:IP` を添えて即座に落とし、正体を報告させる。

### 5. 検証は Unicorn Engine をオラクルとした比較実行 (co-simulation) を主軸にする

Unicorn は QEMU の CPU エミュレーション部をライブラリ化したもので、
「正確なx86」がRustから数行で呼べる。同じ初期状態 (レジスタ・フラグ・メモリ) を
自作CPUとUnicornの両方に与えて**1命令だけ**実行し、実行後の全状態を突き合わせる。

生成は完全なランダムバイト列ではなく**命令テンプレート**方式にする。
「このオペコードはこういう形」を定義し、オペランドと初期値だけを振る。
初期値には 0x00/0x01/0x0F/0x10/0x7F/0x80/0xFF といった境界値を高頻度で混ぜる。
AF や OF は境界を踏まなければ姿を現さないためである。

### 6. 状態空間が小さい命令は、ランダムではなく総当たりで検証する

十進補正 (DAA/DAS/AAA/AAS) は AL の値と CF/AF だけで分岐が決まり、
状態空間が 256 × 3 × 4 しかない。ランダム生成では特定の1点を踏み損ねる。

### 7. 緑のテストは、変異テストで検出力を確認してから信用する

テストが通ったとき、実装が正しいのかテストが何も見ていないのかは区別できない。
意図的にバグを注入 (mutation) して検出されることを確認してから、緑を信用する。

### 8. BIOSは実装せず、必要なサービスだけ高位エミュレート (HLE) する

実BIOS ROMを動かすのは目的ではない。`INT` 命令をフックし、必要なサービスだけ
ホスト側の関数として実装する。

## 根拠となった実測

決定6と7は机上の理屈ではなく、実際に踏んで決めた。

ADCのAFフラグ計算からキャリー加算を落とす変異は、ランダム生成で即座に捕まった。

```
[ADC r/m8,r8] code=[10, d4] regs=[8000, 19ff, ...] flags_in=CF|PF
  FLAGS: ours=PF|SF oracle=PF|AF|SF (差分 AF)
```

一方、DAAの境界値を `0x99` から `0x9A` にずらす変異は、**ランダム3000ケースでは
検出できなかった**。ALがちょうど 0x9A になるケースを踏み損ねたためである。
総当たりに切り替えた途端、一発で捕まった。

```
co-sim mismatch [DAA] code=[27] AX=009a flags_in=-
  AX: ours=00a0 oracle=0000
```

## 結果

### 得られたもの

- Blarggのような網羅テストROMが無い領域で、**テストを無限に生成できる**
- 差分が「どの命令の、どの入力で、どのフラグが」という粒度で出る
- 大きなリファクタの安全網になる。実際 `cpu.rs` を6ファイルに分割した際、
  約9万ケースが番人として機能した

### 代償

- **実行時間**。1ケースごとにUnicornインスタンスを作るため、フルスイートで約2分かかる。
  日常の開発ではブートセクタE2E (即座に終わる) を回し、co-simは節目で流す
- **未定義フラグの管理**。x86には仕様上結果が未定義のフラグがある
  (シフトのOF、MUL後のSZAP等)。テンプレートごとにマスクを持つ必要がある
- **オラクル都合の偽陽性**。QEMUは自己書き換えコードを検出すると命令をやり直すため、
  ランダムな書き込み先がコード領域に当たると「実行されなかった状態」と比較してしまう。
  差分が出たとき、まず自分を疑うが**オラクルの使い方も疑う**必要がある
- Unicornのビルドに数分かかる (初回のみ)

## 検討した代替案

**RISC-Vで作る**: 命令が直交していて実装は遥かに楽だが、目的が
「現代PCの成り立ちを理解する」ことなので、歴史の地層があるx86の方が題材として合う。

**既存のx86テスト (test386.asm 等) を使う**: カバレッジが固定で、
自分が今書いた命令を狙って叩けない。co-simと併用は可能なので将来の選択肢には残る。

**期待値テーブルを自作する**: フラグの正解値を人力で作ることになり、
それ自体が仕様の再実装になる。誤りが混入したとき気づけない。
