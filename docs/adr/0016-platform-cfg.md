# ADR-0016: プラットフォーム分岐の作法 — 同じコードでターゲット別の速さを取る

- 状態: **決定** (2026-08-13 ユーザー発案)
- 日付: 2026-08-13
- 関連: [ADR-0015](0015-cpu-opt-phase-close.md) (native最適化フェーズ終了)、
  [ADR-0014](0014-external-review-hotpath.md) (D3 = wasm境界検査の残置)、
  [pitfalls 11](../explanation/pitfalls.md) (ノイズ床)

## 背景

同じ最適化がターゲットによって勝敗を変えることが実測で分かっている:

- 境界検査の省略: M1ネイティブでは**ワッシュ** (分岐予測で既にタダ) だが、
  wasmでは実コストの可能性が残る (D3、未判定)
- B5 (トレース化): M1で+8%悪化、x86でも+4%悪化と**両方で確認して**棄却した
- 判別則(1)〜(4)はM1のOoO実測則 — x86やwasmランタイムでは影の形が違う

つまり「この手は効くか」に単一の答えは無く、**ターゲットごとに裁く**必要がある。
Rustの `cfg` はこれをコンパイル時・コストゼロで表現できる。

## 決定

1. **ターゲット分岐は `#[cfg]` で行い、「そのターゲットの実測で勝った手」に
   だけ使う。** 判定は各ターゲットの物差し (native: bootphase交互A/B /
   wasm: headless.mjs、床±2%) で独立に行う — **あるターゲットの棄却を
   別のターゲットへ移送しない** (D3で確立した原則の一般化)
2. **CIはコードで分岐させない。** CIの仕事は出荷物と同じバイナリを裁くこと —
   CI専用の道を作った瞬間、門番は別物を見ている。CIで変えてよいのは
   閾値・並列度などの**環境変数だけ** (REGRESS_MIN_MIPS方式)
3. **分岐は関数境界で。** ホットループの行内に `#[cfg]` を撒かない —
   「嵩で払う」(translate-first増分3の+17%) はcfgでも起きる。
   同名関数を `#[cfg]` で差し替える形にし、意味論は同一・速い道だけ変える
   (「意味論の原本は1つ」の維持)
4. **決定性は全ターゲット共通の門番。** 同じイメージなら実行命令数は
   native/wasm/Windows/Linuxでビット同一 — cfg分岐が意味に触れたら
   ここで即death (OS起動回帰+スナップショット段が見張る)

## 最初の適用候補 (それぞれ実測してから)

| ターゲット | 候補 | 出自 |
|---|---|---|
| wasm32 | 境界検査の省略 (get_unchecked、証明つき数行) | D3。nativeワッシュ実装が `exp/hotpath-batch2` に保全済み |
| wasm32 | Uop/Entryの痩身系 (wasmはメモリ単価が高い — dcacheがwasmで約2倍効いた前例) | exp/dcache-soa 等の再審 |
| x86_64 (WSL2/Windows) | M1でワッシュだった手の再審 (hitsカウンタ・HotState等 — OoOの影の形が違う) | 各expタグ |

## 教訓の先取り

寝かせタグ (`exp/*`) は「その時点・**そのターゲット**の前提でこうだった」の
記録である。プラットフォームが増えるたび、台帳は再審の候補リストとして
もう一度価値を持つ。
