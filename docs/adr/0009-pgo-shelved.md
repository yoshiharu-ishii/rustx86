# ADR-0009: PGOは効いたが寝かせる — 運用判断を開発に持ち込まない

- 状態: **決定** (2026-08-11 ユーザー決定: 常設見送り・タグ保存・復帰条件つき)
- 日付: 2026-08-11
- 関連: [ADR-0008](0008-template-jit.md) (wasm凍結→汎用路線の文脈)、
  [perf.md](../perf.md) (寝かせ台帳)、タグ [exp/pgo-build](https://github.com/yoshiharu-ishii/rustx86/releases/tag/exp%2Fpgo-build)、PR #64 (クローズ)

## 背景

wasmバックエンド凍結 (ADR-0008ロードマップ改訂) を受けて「汎用最適化」路線へ
転換した直後、第一手としてPGO (プロファイル誘導最適化) を試した。
PGOは2回コンパイルの間に本番ワークロードを1回走らせ、「どの分岐がどちらへ
倒れるか」の実測をLLVMに渡して機械語の並び・インライン判断を組み直させる
ビルド技法である。ソースは1行も変えない。

## 実測 (M1・熱あり・交互A/B 5周全勝)

| | 通常ビルド | PGO |
|---|---|---|
| vmlinux 580M | 9.6〜10.0s | **7.2〜7.8s (約-25%)** |
| bzImageフル 970M | 13.0s | **11.0s** |

命令数はビット不変 (580M/970M) — 意味の後退なし。効き幅が大きいのは、
インタプリタの正体が「巨大なディスパッチmatch+ヘルパ呼び出しの束」で、
コード配置と分岐予測の当たり外れが利くため (CPythonの公式バイナリが
PGOで10〜30%取るのと同じ構図)。

## 議論の記録 (なぜ「効いたのに見送り」なのか)

**賛成論 (入れる理由):**

- -25%は今年最大級の単発効果。維持コストはスクリプト1本
- 意味論は不変 — 対応OSリスト (v86的な広がり) を増やしも減らしもしない。
  訓練に無いOSでも「壊れる」方向の作用はゼロで、最悪「効きが薄まる」だけ
- CPython・Chrome/Firefox (V8/SpiderMonkey)・QEMU類と、このクラスのソフトの
  定番技法。ハイパーバイザ (VBox/VMware) が使わないのはVT-xでゲストを実CPUに
  直接走らせていて削る配管が無いからで、rustx86の同類はQEMU TCG/CPython側
- ホスト非依存 (M1でもWSL2 x86_64でも同じ手順)

**反対論 (見送りの決め手 — ユーザー):**

- **「遅い→プロファイルが古いのでは→再訓練すべきでは」という運用判断が
  半永久に開発へ付いて回る。** ワークロードが増えるたび・コードが変わるたびに
  この問いが発生する。「毎回遅いから最適化しないとという判断を組み込みたくない」
- **交互A/Bの測定文化と相性が悪い。** 公平な新旧比較には毎回再訓練が要り、
  プロファイル差分が効果測定のノイズ源になる。台帳の数字の土台が揺れる
- 速さは**設計** (C7・JIT・Cranelift — 一度入れたら終わりの構造改善) で取る、
  という方針の芯を守る

つまり争点は「効くか」ではなく (効く)、**「開発プロセスに常設の判断を
1個増やしてよいか」**であり、答えはNoとした。

## 決定

- **常設は見送り。** ただし**捨てない**: 実験一式 (tools/build-pgo.sh + 実測) は
  タグ `exp/pgo-build` に保存 (B3/B5と同じ寝かせ方)。台帳 (perf.md) にも記録
- 開発の測定・A/Bは今後も**素のビルド**で行う (これが台帳の基準系)

## 復帰条件 (寝かせ = いつでも起こせる。2026-08-11 ユーザーが層で整理)

**原則: 「一度動かして、その結果を最適化に使い回す」系の技法は、それが
製品の動作モデルそのものになる Firecracker 的運用の段 (microVM、Tier 8/9) に置く。**
Firecrackerの本体機能 (スナップショット復元・プリウォーム) はまさにこのクラスで、
あの層では「訓練済み・温め済み」は隠れた依存ではなく**仕様**である。
逆に汎用エミュレータ層に置くと、任意のアプリに対して「なぜか特定ワークロード
だけ速い」という暗黙の依存が生まれる — アプリ層に悪さをする。

1. **Firecracker的運用を導入する段** — microVMのイメージ焼き・配布パイプラインの
   一部としてPGOを組み込む。訓練セットは「そのmicroVMが実際に走らせるもの」で、
   ワークロード依存はそこでは欠点でなく狙いになる
2. **どうしようもなくなったとき** — 設計側の最適化 (C7・JIT・Cranelift) を
   出し切っても目標 (フルブート10秒 / ~100 MIPS) に届かない場合の最後の-25%。
   そのときは運用判断を殺すルールとセットで入れる: 訓練セットは
   「3OS起動回帰スイートと同一」に固定 (回帰に足す=訓練にも載る、の一本化)

## 教訓 (メモリにも保存済み)

最適化を評価する軸に「効き幅」だけでなく**「一度入れたら終わりか、
運用判断が付いて回るか」**を加える。後者は効いても寝かせ、前者 (設計改善) を
優先する。効いた実験を黙って取り下げない — 議論と復帰条件をADRに残す
(本ADRがその実例)。
