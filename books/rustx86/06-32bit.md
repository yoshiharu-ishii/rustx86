title: "32bit命令はモードと独立している"
---

FreeDOS を載せようとして、こんな命令で止まりました。

```
53                  PUSH BX
66 9C               PUSHFD                  ← 32bitオペランドサイズ・プレフィクス
66 58               POP EAX
66 0D 00 00 04 00   OR EAX, 0x00040000      ← bit18 = AC フラグ
```

**386 と 486 を見分ける定番の CPU 判定**です。カーネルは 8086 ビルドなのに、
起動時に走るユーティリティが 386 命令を使っていました。

## 「32bit化」は2つの別の話だった

ここで発見がありました。**`0x66` はプロテクトモードと独立しています。**

`0x66` は「32bit モードにする」プレフィクスではなく、
**既定のオペランド幅をひっくり返す**プレフィクスです。

| モード | 既定の幅 | `0x66` が付くと |
|---|---|---|
| リアルモード | 16bit | **32bit** |
| プロテクトモードの32bitセグメント | 32bit | **16bit** |

だから GDT もセグメントディスクリプタも特権リングも実装せずに、
**プレフィクスだけを先に動かせます**。

一般に「32bit化」と呼ばれるものは、実は

- **命令セット** (`0x66`/`0x67` プレフィクス、`0x0F` 二バイト空間、SIB バイト)
- **モード** (GDT、ディスクリプタ、特権チェック、ページング)

という 2 つの別の話でした。前者だけ先にやれます。

## 器を作り直す必要が無かった

レジスタは連載の最初から `u32` で持っていました。

```rust:core/src/cpu/mod.rs
pub struct Cpu {
    pub regs: [u32; 8],
    /// ES CS SS DS
    pub sregs: [u16; 6],
    pub ip: u16,
    pub flags: u32,
}
```

そして 16bit 書き込みが**上位を保存する**形になっていました。

```rust:core/src/cpu/mod.rs
fn set_reg16(&mut self, r: usize, v: u16) {
    self.regs[r] = (self.regs[r] & 0xFFFF_0000) | v as u32;
}

/// 32bitレジスタ (EAX〜EDI)。
///
/// **レジスタは最初から `u32` で持っている**ので、386拡張のために
/// 器を作り直す必要は無かった。16bit命令が上位16bitを保存するのも
/// [`set_reg16`](Self::set_reg16) がそう書いてあるからで、
/// 実機と同じ「同じ器の下半分を見ている」関係がそのまま出ている
fn reg32(&self, r: usize) -> u32 {
    self.regs[r]
}

/// 32bit書き込みは**上位も含めて全部置き換える** (16bitのような保存はしない)
fn set_reg32(&mut self, r: usize, v: u32) {
    self.regs[r] = v;
}
```

実機の EAX と AX の関係がそのまま出ています。

## 幅は型ではなく実行時のフラグで選ぶ

素直にやると、分岐表が幅ごとに 2 本に膨れます。それを避けるため、
**入口で吸収する**形にしました。

```rust:core/src/cpu/mod.rs
/// 幅を実行時に選ぶレジスタ読み出し
fn reg_w(&self, r: usize, wide: bool) -> u32 {
    if wide { self.reg32(r) } else { self.reg16(r) as u32 }
}

/// 幅を実行時に選ぶレジスタ書き込み
fn set_reg_w(&mut self, r: usize, v: u32, wide: bool) {
    if wide {
        self.set_reg32(r, v)
    } else {
        self.set_reg16(r, v as u16)
    }
}
```

```rust:core/src/cpu/alu.rs
/// 幅を実行時に選ぶALU。`0x66` の有無で16bitと32bitを切り替える。
///
/// **呼ぶ側に同じ形のコードを2本書かせない**ための入口である。
/// 分岐表 (`cpu/mod.rs`) が幅ごとに倍に膨れるのを防ぐ。
pub fn alu_w(c: &mut Cpu, op: u8, a: u32, b: u32, wide: bool) -> u32 {
    if wide {
        alu32(c, op, a, b)
    } else {
        alu16(c, op, a as u16, b as u16) as u32
    }
}
```

これで分岐表は 1 行足すだけで済みます。

```rust:core/src/cpu/mod.rs
1 => {
    // r/m16,r16 または r/m32,r32 (`0x66` が付いていれば後者)
    let (reg, rm) = modrm(m, &d);
    let w = d.opsize32;
    let a = read_op_w(m, &rm, w);

    let r = alu_w(&mut m.cpu, kind, a, b, w);
    if kind != 7 { write_op_w(m, &rm, r, w); }

```

なお **8/16/32 で ALU の構造が完全に平行している**のは偶然ではありません。
386 が 16bit の意味論をそのまま広げる形で拡張されたからです。

## スタックの幅とSPの幅は別

`PUSHFD` の実装で気づいたことです。

```rust:core/src/cpu/operand.rs
/// 32bitのpush。
///
/// **SP自体は16bitのまま**である。`0x66` はオペランドの幅を変えるだけで、
/// スタックポインタの幅はセグメントのBフラグ (プロテクトモード) が決める。
/// リアルモードではBが立たないので、SPは16bitで回り続ける
pub fn push32(m: &mut Machine, v: u32) {
    let sp = m.cpu.reg16(SP).wrapping_sub(4);
    m.cpu.set_reg16(SP, sp);
    m.write32(linear(m.cpu.sregs[SS], sp), v);
}
```

**オペランドの幅・アドレスの幅・スタックの幅は、それぞれ別のものが決めています。**
`0x66` は 1 つ目、`0x67` は 2 つ目、セグメントの B フラグが 3 つ目です。

## 幅対応を忘れると、静かに壊れる

ここが一番苦労したところです。実装したのに動かない。しかも
**まったく関係ない番地で「`0F 4C` (CMOVL) が未実装」**という顔をして倒れる。
Pentium Pro の命令が 8086 向けビルドに出てくるはずがありません。

原因は `TEST EAX, imm32` の幅対応漏れでした。

```rust:core/src/cpu/mod.rs
// TEST AX,imm16 / EAX,imm32。
// **即値の長さが幅で変わる**ので、ここを16bit固定にしていると
// `0x66` が付いた瞬間にIPが2バイトずれ、以後はデータを命令として食う。
// 実際それで遠くの番地まで暴走した (0x66 の記録がそれを教えてくれた)
0xA9 => { let w = d.opsize32; let b = fetch_w(m, w); let a = m.cpu.reg_w(AX, w); alu_w(&mut m.cpu, 4, a, b, w); }
```

即値を 16bit で読むので **IP が 2 バイトずれ**、以後はデータを命令として
食い始めていました。

見つけたのは、こういう仕掛けを入れたからです。

```rust:core/src/lib.rs
/// `0x66` (オペランドサイズ) を付けて実行されたオペコード。
///
/// **幅対応を忘れた命令は静かに壊れる。** 即値や退避の長さが変わるので、
/// 16bitのまま実行するとIPがずれ、以後はデータを命令として食い始める。
/// panicも出ないまま遠くで暴走するので、**来たものを控えておく**。
pub prefixed_ops: std::collections::BTreeSet<u8>,
```

```rust:core/src/cpu/mod.rs
if d.opsize32 {
    m.prefixed_ops.insert(op);
}
```

止まったときに出すと、一発でした。

```
--- 0x66 を付けて実行されたオペコード ---
  0x02 0x0d 0x21 0x33 0x39 0x50 0x53 0x58 0x5b 0x8b 0x9c 0x9d 0xa9 0xb9
                                                                  ^^^^ 未対応
```

**panic も出さずに静かに壊れるものは、記録を取るしかありません。**

## 名乗るものを1ビット間違えた話

`POPFD` を実装するとき、書き換え可能なフラグに **AC (bit18)** を含めてしまいました。
すると FreeDOS が「このCPUは486以上だ」と判断し、**`CMOVcc` (Pentium Pro) を
使い始めました。**

```rust:core/src/cpu/mod.rs
0x9D => {
    let f = pop_w(m, d.opsize32);
    // 書き換えられるビットだけ受け取る。
    //
    // **AC (bit18) は受け付けない。** これは486で入ったフラグで、
    // 「立てて書き戻し、残っていれば486以上」という判定に使われる。
    // 一度これを通してしまったところ、FreeDOSが486と判断して
    // `CMOVcc` (Pentium Pro) を使い始めた。
    //
    // 幅を32bitにできる = 386、ではあるが**486ではない**。
    // 名乗るものを1ビット間違えるだけで、相手は別の道を歩き出す。
    m.cpu.flags = (m.cpu.flags & !0x0FD5) | (f & 0x0FD5) | 0x0002;
}
```

**エミュレータは「何であるか」を正確に名乗る責任があります。**
1 ビット多く名乗っただけで、相手は持っていない命令を使い始めます。

## x87 は「何もしない」のが正しい

もうひとつ、直感に反して面白かったのがこれです。

```rust:core/src/cpu/mod.rs
// --- x87 (0xD8-0xDF): コプロセッサは載せない ---
//
// **何もしないのが正しい。** 8087を挿していない8086では、ESC命令は
// 実効アドレスを計算してダミーの読み出しをするだけで、メモリも
// レジスタも書き換えない (本来は隣に座った8087がバスを盗み見る)。
//
// FPUの有無を調べるコードは、番兵を置いた場所に `FNSTSW` で書かせて
// **書き換わらなかったこと**で不在を知る。だからここで気を利かせて
// 何か書くと、逆に「FPUが在る」と誤認させてしまう。
//
// ModRMだけは読む — IPを正しく進めないと次の命令がずれる。
0xD8..=0xDF => {
    let _ = modrm(m, &d);
}
```

**気を利かせて何か書くと、逆に嘘になる。** 装置が無いことを表現するのに、
何もしないのが正解という場面があります。

## 到達点

これで FreeDOS が `A:\>` まで起動しました。

```
A:\>dir
 Volume in drive A is FD14-BOOT
 Directory of A:\

KERNEL   SYS        46,485  05-14-21  3:32a
ELIZA    EXE         5,968  08-08-26  4:19p
ZMIY     EXE        10,698  08-08-26  4:19p
ROW4T    COM        13,408  08-08-26  4:19p
A:\>
```

次はプロテクトモードとページング、そして 32bit Linux です。
モードの側 — GDT、ディスクリプタ、特権チェック — が残っています。

命令表は格子で畳めましたが、**本丸は命令表ではありません**。
同じ `MOV DS, AX` が、リアルモードでは単なる数値の代入、
プロテクトモードでは**テーブル引きと権限検査**に化ける。
同じ命令の意味が変わるのが、モードという概念の正体です。

最後に、この本を通していちばん効いた道具を挙げるなら**診断**でした。

- `unhandled_io` — 誰も名乗り出なかったポート番号
- `prefixed_ops` — `0x66` が付いたオペコード
- `video_modes` — 要求されたビデオモード
- 割り込みベクタの持ち主

どれも「動かないときに何が起きたか」を答えるためのもので、
機能としては 1 行も増えていません。それでも、**実 OS を動かす段階では
これがあるかないかで進む速度がまるで違いました。**
