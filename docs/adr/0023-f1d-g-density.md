# 0023: F1d-g — 生成コードの密度 (条件インライン化とcc死储の省略)

日付: 2026-08-17 / 状態: 採用 / 関係: [0022](0022-cpu-round3-before-gfx.md), [0013](0013-f1c-freeze.md)

## 背景

F1d-f (PR #181/#182) でブートは初の黒字 (-7%) になったが、gcc窓は-14%のまま。
実測が示した敵は**カバレッジではなく生成コードの実行密度**である:

- カバレッジ51→58.5%・平均8.5命令/入場に上げても壁時計は不変 (f1とf2は同着)
- 入場税は健全 (窓内入場34M回、固定費は回収できる粒度)
- 残るコストは毎命令の中身: ALUごとに**cc材料6ストア**、Jccごとに**h_cond
  ヘルパ呼び** (Jccは約1/7命令)、毎opのゲストレジスタのロード/ストア

## 決定

密度を2つの梃子で上げる。どちらも**エミット時に確定する局所解析**だけで、
実行時の新しい状態を持たない (決定性はビット同一のまま):

1. **g1: cc死储の省略** — op i のcc材料ストアは、op i+1 が「観測されうる前に
   ccを完全上書きする純レジスタop」なら省く。観測点 = 脱出しうるop (メモリ形)、
   ヘルパ (h_cond/h_cf/shift/grp3)、ブロック出口、Jcc。隣接する上書きだけを
   対象にする (xor-zeroing → test の類)
2. **g2: 条件判定のインライン化** — cc設定opの直後のJcc/setccは、材料が
   ホストレジスタ (w10/w11/w13) に生きている間に**ホストフラグで判定**する:
   - SUB/CMP/ADD系: `subs/adds` (8bitは`lsl 24`で上位バイトに寄せて桁を合わせる)
   - OR/AND/XOR系: 結果w13を `cmp #0` (x86はCF=OF=0 → ARMはC=1/V=0で
     全16条件の真理値が一致することを確認済み)
   - ARM条件への写像: E→eq NE→ne B→lo AE→hs BE→ls A→hi S→mi NS→pl
     O→vs NO→vc L→lt GE→ge LE→le G→gt。**P/NPとADC/SBB/INCDECは従来どおり
     h_cond** (写像なし・材料に cin が絡む)

## 「意味論の原本は1つ」との折り合い

条件写像は意味論の二重実装に半歩踏み込む。許す理由と守り:

- cc**材料**の直書きは既にalu_lazyの写しとして前例がある (F1d-a以来)。
  今回はそこに「材料→条件」の有限写像 (6 kind × 14 cc × 2幅) が加わるだけ
- 写しの正しさは**差分テストで全数照合**する: `tests/cond_inline.rs` が
  全kind×全cc×両幅×境界値операндでJIT on/offの結果 (setcc値+6フラグ) を
  突き合わせる。指紋2コース (jboot/jcmd) とcosimが上に乗る
- 写像は表1枚に閉じ込め、遅延フラグの評価器そのもの (cc_cf/cc_of…) には
  一切触れない

## 棄却・保留

- **ゲストレジスタのホストレジスタ常駐化**は今回は見送り (callee-saved
  x22-x28に空きはあるが、全ヘルパ境界でのflush/reload規律が要る大工事)。
  g1/g2の実測を見てから台帳で再訪する
- ブロック内cc完全遅延 (出口でまとめて書く) は、脱出点ごとのflushが
  g1の隣接省略と大差ない割に複雑なので保留
