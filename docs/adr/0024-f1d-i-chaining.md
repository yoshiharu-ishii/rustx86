# 0024: F1d-i — TB chaining (直接ブロック連結) と決定性の契約

日付: 2026-08-18 / 状態: **実装検証の上で不採用** (実装は feat/f1d-i-chaining ブランチに寝かせ — 下の追記参照) / 関係: [0023](0023-f1d-g-density.md), [0022](0022-cpu-round3-before-gfx.md)

## 背景

第2ラウンド調査 ([jit-roadmap2.md](../reference/jit-roadmap2.md)) の結論。
実測で1入場≈90-100ホスト命令の固定費 (入場機構8% + core清算 + 出入り26命令) を
毎ブロック払っている。QEMU TCGの主砲 = ブロック末尾をパッチして次ブロックへ
直接飛ぶ **TB chaining** でこれを消す。QEMUはicountモードと同居させている
実績があり、決定性と両立できる。

## 決定 (v1の範囲)

**直接分岐だけ**を連結する: 終端Jmpと、両側焼きJccの成立側。条件は
**着地が同一物理ページ内** (paが焼き時に確定する — coreの連結ループと同じ制約)。
ret/間接分岐は対象外 (次の玉=間接分岐キャッシュ)。呼び先が未焼きなら従来どおり
出口へ (退出してtry_enter経由)。

## 決定性の契約 (これが本体)

1. **tick境界は不変**: 予算 (budget = min(鎖残り+1, tick_countdown)) を
   レジスタ w23 で持ち回す。連結先へ飛ぶ前に `subs w23, w23, #n_B` し、
   足りなければ退出 — **チェーン全体が入場時の予算内に収まる**ので、
   ブロック内どころかチェーン内でもtickは起きない。割り込みが保留に
   なるのはtick時だけなので、受付位置は毎命令実行と同一のまま
2. **清算は退出時に一括**: 実行命令数を w24 に積算し、出口で
   w0 = w24 + w15 を返す。coreの清算式 (tsc/tick_countdown/extraの前払い
   構造) は総和だけで決まる — 分割位置に依存しない
3. **ipは各ホップで更新**: 連結スタブが従来の出口と同じ ip += delta を
   実行してから飛ぶ。連結先の出口のdelta計算は「自ブロック頭からの差分」の
   前提を保つ
4. **世代照合は連結先の頭で**: スタブに焼き時のB世代を埋め、実行時に
   page_genと照合。落ちていたら退出 (ipはB頭・実行数はAまで — 従来の
   出口と同じ可視状態)

## 生存の契約 (ダングリング防止)

世代照合は**ゲスト可視のSMC**しか守らない。ホスト側の退去 (スロット衝突・
損益降格) はゲスト世代が動かないので、**リンク剥がしの台帳**で守る:

- Blockは incoming (誰が自分に飛んでくるか: from_slot / from_serial /
  分岐オフセット / 元命令語) を持つ
- ブロックを捨てる全経路 (世代落ち・降格・衝突退去) は **drop前に**
  incomingを歩き、生きている飛び元の分岐を元の `b ->exit` に書き戻す
  (mprotect RW→書換→RX→icache invalidate)。serial照合で飛び元自身の
  入れ替わりも検出
- 単一スレッド前提 (RTと同じ規律) なので、剥がしとdropの間に実行は挟まらない

## リンクの張り方

- スタブは焼き時に**プレースホルダ定数で全命令を先に焼く** (レイアウト固定)。
  リンク時はmovz/movkのimm16とsubsのimm12のビット畑だけ書き換える —
  実行時に命令を組み立てない
- リンク試行はbake時 (自己ループは即結線) と、損益再審の境界 (256入場ごと —
  既存の分岐に相乗り)。毎入場のリンク探索はしない
- 連結先へは**プロローグを飛ばして本体へ**入る (フレームは飛び元が積んだ
  ものを共有し、出口が一度だけ畳む)

## 損益観測への影響 (既知の歪み)

連結ホップはtry_enterを通らないので enters/execd は表口の入場だけを数える。
連結で熱いブロックが「入場が稀」に見えて降格されうるが、降格はリンク剥がしを
経由するので**正しさは無傷** (性能上の歪みのみ)。v1は容認し、実測で問題が
見えたら再訪する。

## 棄却・保留

- **チェーン内清算の逐次化** (ホップごとにtsc更新): 一括と可視結果が同じで
  遅いだけ — 棄却
- **クロスページ連結**: paが焼き時に確定しない (マッピング依存)。変換を
  スタブに埋める案は複雑 — 保留
- **fallthrough (非終端末尾) の連結**: coreの連結ループが同等の仕事を
  しているので v1 では見送り、chainingの実測後に再訪

## 追記 (2026-08-18、実測後の裁定)

契約はすべて成立した (指紋2コースビット同一一発・剥がし台帳が実地で稼働) が、
**壁時計は同着〜-1%で不採用**。原因は tick粒度64命令が予算の天井で、
チェーンが数ブロックで必ず表口へ戻ること (詳細は perf-log 2026-08-18)。
診断実験で tick=256 にすると off 85.8 vs on 90.7 MIPS と大きく効くが、
**chaining有無はその条件でも同着** — 利得は粒度そのもの。tick粒度は
ゲスト可視のタイミング変更 (ネットワークRTT・golden基準値) なので
ユーザー裁定の台帳項目とする。
