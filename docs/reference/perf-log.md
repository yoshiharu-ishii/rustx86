# 最適化の実験記 (時系列・追記専用)

[perf.md](perf.md) が「地図」(現在地・カタログ・規律)、ここが「物語」—
日付つきの実験の経過と謎解きの記録。横断の教訓は [pitfalls.md](../explanation/pitfalls.md) へ、
判断の理由は [ADR](../adr/) へ。

## 2026-08-10: B4後の現在地とプロファイル

| 経路 | シェル到達 | 実効速度 |
|---|---|---|
| vmlinux 直接ロード | 580M命令 / 8.8s | 66.2 MIPS (P1a後16.3s → C4 → B4で半減) |
| wasm (headless) | 600M / 13.6s | 44.2 MIPS (P1a前は50〜66s — 4倍弱) |
| ブラウザ実機 | 21s (ユーザー実測) | P1a後45s → P1b後38s → 21s |
| スナップショット復元 | — | 0.1〜1s (起動しない、が最速) |

プロファイル (boot中サンプル上位): cpu::step 33% (フェッチ+ディスパッチ) /
modrm 13% / memmove 12% (CPU控え+REP) / translate_for 8%。

**「なぜ~30 MIPSどまりだったのか」の当時の理解**: 1命令34ns = M1の約110サイクル。
毎命令「フェッチ→プレフィクスループ→巨大match (間接分岐の予測ミス) →
ModRM再デコード→実行→帳簿」を踏む古典的スイッチ型インタプリタの相場 —
コードが悪いのではなく構造の上限。この理解がP1 (dcache) 以降の全設計を導いた。

### つぶした順 (2026-08-10深夜時点の総括)

```
済み:    A1 A2(寝) B1 B2 B3(寝) B4 B5(寝) C1 C2 C4 C4b C5(寝) D2(寝) E1 E2 E6
         — 13→78 MIPS
方針転換 (ユーザー決定): Tier進行の前に100 MIPSを取り切る。
理由「エミュレータの速さは以後すべての検証の単価」。
経過:   C1 -3〜4% (期待10〜25%はB4前の前提)、C4b -17% (memmove 11%の正体は
        Cpu丸ごと控えだった)。以降は全滅: D2・TLB配列化・C5 (+10%悪化)・
        B5ブロック化 (+8%悪化) — インタプリタ内の再配置はもう動かない
結論:   素で~78 MIPS。構造の上限に到達 — 100へはF1テンプレートJITが本命昇格
```

**B3の教訓**: 最適化の取り分は積み木ではない。B4が「毎命令の固定費」を先に
食い尽くしたので、同じ費目を狙うB3にはもう払い戻しが残っていなかった。
カタログの期待値は**着手時点の前提**の値であり、先行する最適化が前提を書き換える。

## 2026-08-11: ホスト横断の実測 (同じイメージ・同じ命令数 — 全マス完了)

| ホスト | ネイティブ bzImage (970M) | ネイティブ vmlinux (580M) | wasm bzImage (1000M) | wasm vmlinux (600M) |
|---|---|---|---|---|
| M1 MacBook Air (2020) | 10.7s / **90.7 MIPS** | 7.3s / 79.5 | 16.2s / 61.7 | 10.0s / 60.3 |
| Ivy Bridge素のWindows (2012) | 23.9s / 40.6 | 15.2s / 38.2 | 36.9s / 27.1 | 21.6s / 27.8 |
| 同マシンのVirtualBox VM (Ubuntu) | 26.1s / 37.2 | 16.0s / 36.3 | 36.0s / 27.8 | 21.3s / 28.2 |

- **仮想化の税はわずか5〜9%、wasmではほぼゼロ** — エミュレータは純粋な
  ユーザー空間演算でVM exitをほぼ起こさない。M1との2.4倍差の正体はCPU世代差

- **命令数は全3ホスト×2経路×2ランタイムでビット同一** — 決定性がOS・ISA横断で成立。
  Tier 8 (ホスト混在のスナップショットfork) への布石
- 2012年の企業PCでもwasm 27 MIPS = ブート37s — 「古いPCにブラウザだけでLinuxが
  立つ」の下限値

## 2026-08-12 互換の代金を測る — test386完全合格の前後で交互A/B

test386完全合格 (PR #78) はタダではない。毎命令に足したもの:
データアクセスのセグメントlimit検査 (data_addr)・A/Dビット反映の空チェック
(flush_ad)・フォールト控えの条件拡大 (paging時のみ→PE時)・POPF/回転の
フラグ規則。命令数は**580Mで不変** (意味の同一性はOS起動回帰が保証) なので、
差は純粋に毎命令の単価。

計測: `bootphase images/vmlinux-lts` を互換前 (main@697b7b4、worktreeで焼き直し)
と互換後 (main@e72c2c7) で交互に5周。

| round | 互換前 | 互換後 |
|---|---|---|
| 1 | 8.2s | 9.0s |
| 2 | 8.3s | 9.1s |
| 3 | 8.2s | 9.4s |
| 4 | 8.3s | 9.1s |
| 5 | 8.3s | 9.4s |

**約+10% (~70 → ~64 MIPS)**。これは「正しさの代金」であり払って正解 —
ただし取り返す道はある。検査のほぼ全ては Linux の平坦セグメント
(base=0/limit=4GB) では**恒真**なので、ロード時に平坦と判定して控えれば
1分岐で飛ばせる (カタログ S1)。JIT (F1c) はこの検査ごと生成コードに
畳み込めるので、互換税はJIT時代には別の形で消える見込み。

## 2026-08-12 互換税の取り返し S1〜S3 — 見立ては外れ、-2〜4%で打ち止め

S1 (平坦セグメント高速路) が本丸のはずだった — 検査はLinuxの平坦セグメント
で恒真だから。ところが単独で**-2%**しか返らない。S2 (flush_adの空チェックを
インライン化 — 毎命令に非インラインcallが1本入っていた) で合算-3〜4%、
S3 (TLBエントリ16→12バイト、旗をbaseの下位ビットへ) は熱ノイズに埋もれて
単独寄与を判定できず (構造としては正しいので採用)。

| round (冷却後) | main | S1+S2+S3 |
|---|---|---|
| 4〜8の帯 | 9.1〜9.5s | 8.9〜9.3s |

教訓: **「検査のコスト」は検査の分岐ではなくコードの嵩** — 分岐自体はM1の
予測が隠す (B5/C5と同じ構図)。恒真の検査を飛ばしても、増えたコードがI側を
圧す分は返らない。残り~6%は追わず、F1c (Cranelift) で検査ごと生成コードに
畳み込む側に賭ける。

## 2026-08-12 F1c関門プローブ — Craneliftの固定費は回収可能、焼きは背景スレッド前提

wasm版jit-probe (F1a入口の関門) と同じ問いをネイティブ/Craneliftに。
道具は tools/jit-probe-native (使い切りの独立クレート、coreは無依存のまま)。
regs配列へのload/ALU/store連鎖をuopブロックに見立て、opt_level none/speed両方。

| 指標 | 実測 (M1) | 備考 |
|---|---|---|
| 呼び出し | ~3ns/ブロック | wasm版の7nsより安い (C ABI直呼び) |
| uop単価 | 0.28〜0.83ns | インタプリタ16〜36nsの20〜50倍の頭上 |
| 焼き | 53〜76µs (4〜8uop)、276µs (40uop) | wasm手組み6.3µsの~10倍。noneとspeedでほぼ差なし (下部構造が支配) |

損益分岐 ≒ 600実行/ブロック (8uop、70µs÷120ns節約)。熱ブロックの平均実行数は
~15k (580M×カバレッジ0.8÷31k頭) なので**個々のブロックは楽に回収**する。
問題は総額: 31,441頭×~70µs ≒ **2.2秒** — 9秒のブートに前払いで載せたら台無し。
ネイティブはwasmと違ってスレッドがあるので、**焼きは背景スレッド**
(インタプリタが走り続ける裏でコンパイル、できた物から差し替え) が設計要件。
決定性は従来どおり「毎命令の受付点」(案A) を守れば、差し替えタイミングに
よらず命令数は不変にできる — ここはF1c設計 (別ADR) で詰める。

## 2026-08-12 F1c-a 骨格が立った — 決定性ゲート一発合格、カバレッジ16.8%で早くも黒字

jit-native (Cranelift、ADR-0012) の骨格: wasm生成器と同じ意味論契約をCLIFで
写し、焼きは背景スレッド (据え付け時にcollect時ページ世代と照合 — 世代落ち
107件が実際に発生し、ガードが仕事をした)。

初回実行で:
- **決定性ゲート合格**: JIT on/off で命令数 (576,000,000) もシリアルFNVも一致
- **冷間ペア -6%** (12.5→11.7s)、熱間の交互A/Bで -2〜3% (on 4/4勝)
- カバレッジ16.8%・平均ブロック長4.4 — **wasm (F1b-3) と同じ数字で、
  wasmは微赤字、ネイティブは黒字**。ヘルパ税とJS境界の差が単価に出た形

次 = F1c-b: TLBヒット経路とセグメント検査を生成コードに畳み込む (単価)、
その先にブロック連結 (F1c-c)。カバレッジの梃子はwasmで学んだ機構
(タイル張り・走路焼き・永続台帳) が既にcore側にあるので、単価が先。

## 2026-08-12 F1c-b1 TLBインライン — 決定性維持、効果はカバレッジ16.8%ではノイズ内

生成コードにTLBヒット経路を畳み込んだ (ld32/st32/RMW)。coreはrepr(C)の契約と
番地表 (JitLayout: tlb/mem/hidden/vram) の拡張のみ。高速路の条件は保守的 —
ページ跨ぎ・TLBミス・旗不足 (読み:U、書き:W|U|D)・RAM外・VRAM窓は全部
ヘルパ (原本) へ落とすので、**高速路が通るときに限り意味が一致する**構造。
RMWのインライン側はalu_coreのcc材料書き出しを流用 (二重実装なし)。

- 決定性の指紋 (命令数576M+シリアルFNV): on/off一致を維持
- 門番: test386 PASS / cosim / workspace 24suite 全緑
- 冷却A/B 8周: 前半5周はon勝ち (最大-2.3s)、後半ワッシュ。off側が
  12.3〜15.5sで暴れる晩で、理論効果 (~0.3〜0.5s @ カバレッジ16.8%) は
  ノイズに沈む。**F1b-1/2と同じ「単独では測れない資産」** — カバレッジが
  上がった時に単価として効く土台なので採用

結論はまた同じ所へ帰る: **梃子はカバレッジ (16.8%)**。次はopstatsで
語彙外uop分布を採り直し (wasm時代の実測は語彙内81%)、F1c-c (連結) か
語彙拡張かをデータで決める。

## 2026-08-12 ネイティブの語彙分布 (opstats) — 次の語彙はshift・movzx8・8bit ALU族

jboot --features opstats で採り直し (wasm時代のF1b-3と同じ流儀):
語彙内77.4% / 語彙外22.6%。語彙外の上位:

| uop | 動的数 |
|---|---|
| shift r (シフト/回転 レジスタ形) | 29M |
| movzx8 r,[m] | 19M |
| test8 | 13M |
| grp1-8 / grp3-8 / alu8 (8bit ALU族) | 20M |

この4家族 (~85M/130M) を語彙に足せば語彙内~92%。カバレッジ16.8%と
語彙内77.4%の差は分断 (語彙外1命令が走路を切る) なので、頻出の
分断犯を消す効果はブロック長に複利で効く。**F1c-b2 = この語彙拡張**。
シフトのccはlazy flagsの材料形が違う (shift_rot参照) — cc_op拡張が要る。

## 2026-08-12 F1c-b2 語彙v2 — カバレッジ16.8→29.6%、冷却A/B 8周全勝 -7〜9%

分布実測どおり shift r・movzx8/16・test8・8bit ALU族・mov8 (読み形) を語彙化。
capsゲート (CAP_VOCAB2) でwasm生成器 (凍結) には渡さない。実装の型は3種:
- **インライン**: movzx・8bit ALU/test/cmp (alu8_core = cc_w=0の材料書き出し、
  AH形のバイト抽出/挿入込み)、ld8はTLB高速路つき
- **ヘルパ完結 (eager flags)**: shift r (shift_rotの意味論はcc材料に畳めない)、
  grp3b8のNEG (CF上書き)。#PF不能なので脱出も不要 — 一番安い形
- **ヘルパのみ**: ld16 (頻度2M、インライン化は分布が要求してから)

| 指標 | b1 | b2 |
|---|---|---|
| 語彙内 (動的) | 77.4% | **94.7%** |
| カバレッジ | 16.8% | **29.6%** |
| 平均ブロック長 | 4.4 | 4.6 |
| 冷却A/B | ノイズ内 | **off 12.3〜13.5 vs on 11.5〜12.3 (8周全勝、-7〜9%)** |

決定性の指紋 (576M+シリアルFNV) はon/off一致を維持。

**次の梃子はF1c-c (連結)**: 語彙94.7%でカバレッジ29.6%ということは、
ブロックがjccごとに切れる4.6命令 (x86の基本ブロック長そのもの) が壁。
jccの不成立側をブロック内で続ける「両側焼き」= B4 (-43%) のJIT版が本命。

## 2026-08-12 F1c-c1 連結 + c2 閾値掃引 — ブロック長5.9、カバレッジの天井30%の正体へ

**c1 (jcc両側焼き、CAP_CHAIN)**: 途中のjccを「成立なら ip書いてk+1で退出、
不成立なら同じブロックを続行」に。ブロック長4.6→5.9、入回数37M→28M
(ディスパッチ9M回削減)。b2との速度差はノイズ内 (~0.15s < 床) — 構造資産。
決定性指紋は維持。

**c2 (熱閾値の掃引)**: 8 / 64 / 256 を実測:

| 閾値 | カバレッジ | 据付 | 発見 |
|---|---|---|---|
| 8 | **27.6% (悪化)** | 13165 | **早すぎる焼きはタイルの育ちを止める** — JITブロック内を走ると内側の頭 (head_pending) に熱が乗らない |
| 64 (現行) | 29.3〜29.6% | 7347 | |
| 256 | 29.7% | 4382 | 同等。立ち上がりが遅いだけ |

**閾値は梃子ではない。** 30%で飽和する天井の有力容疑は **tick境界の入場制限**
(step_cachedの `jn <= budget`、budget = tick_countdown min chain残 — 長い
ブロックほどtick窓 (64命令) の残りで入場を拒否され、その区間はインタプリタが
走る)。次 = F1c-c3: 入場判定の実測 (拒否回数のカウンタ) → ブロックに

## 2026-08-12 F1c-c3 入場診断 — 天井の解剖と、bzImageでの初の実効

## 2026-08-12深夜 jbootの絶対値の正体 — cranelift依存のコードレイアウト税

ユーザーの指摘「熱でも処理能力でもなく、単純に処理の問題」を追った結果、
**別バイナリの絶対値を比べていた**という計測の落とし穴を発見した。

同じ vmlinux 576M命令を、条件を1つずつ揃えて2バイナリで測った:

| バイナリ | 条件 | 秒 |
|---|---|---|
| bootphase (core example) | run 10M | 9.5〜10.9 |
| bootphase | run **2M** | 9.8〜10.0 |
| bootphase | run 2M + **Box化** | 9.7〜9.8 |
| **jboot (jit-native bin)** | run 2M, Box, JIT=off | **12.0〜13.2** |

Machine構成・Box化・run粒度・serial処理を**全部揃えても** core-example 9.7s
vs jit-native bin 12.7s。差は**リンクされる依存 (cranelift ~3MB) だけ**。
ループボディを空 (m.runのみ) にしても jboot は12.7sのまま — ハーネスの
ロジックではなく、**巨大な無関係コードのリンクでホットループ機械語の
アラインメント/iキャッシュ挙動が変わる**実在の現象 (Mytkowicz 2009
"Producing Wrong Data Without Doing Anything Obviously Wrong")。

### 教訓 (pitfalls行き)

- **絶対値は同一バイナリ内のA/Bでのみ信じる。** 別バイナリ間の絶対値の
  比較は、コードレイアウトで20%以上動くので無意味
- **JITのoff/on (-9〜13%) は正しい** — 同一jbootバイナリの相対だから
- ただし今日の記述「冷間14.2s換算で~12.8s相当」等、**jbootの相対を
  bootphaseの絶対へ貼り付けた換算は撤回する**。真の絶対の物差しは
  bootphase (vmlinux 10s / bzImageフル 14.2s、いずれもJIT非対応)。
  JITの絶対実効を同じ土俵で測るには bootphase にJITフックを載せた
  ハーネスが要る (次の宿題)
- 本番 (Firecracker/ネイティブ配布) は cranelift をリンクした
  バイナリなので、レイアウト税込みの jboot 側の絶対値の方がむしろ
  本番に近い — LTO/PGOでレイアウトが再び動くまでは

## 2026-08-13 F1c 単価攻め3連投の記録と、凍結の決定 (ADR-0013)

ヘルパ税 (ld/st毎にblr)。次 (F1d-d): TLBヒット路のインライン生成 (F1bで
「カバレッジができてから」と降格された梃子の再訪)・8bit語彙・入場税の削減

## 2026-08-16: F1d-d — TLBヒット路のインライン生成 (判定は冷間持ち越し)

32bitロードにTLBインライン高速路を実装 (translate_forヒット路の写し:
リング0の読みは権限検査もA/D更新も無い — probe+合成だけ)。CPL3・ページ跨ぎ・

## 2026-08-17: F1d-e (1) — 定常WL定規jcmdが正しさバグを一撃で暴いた

gcc課程 (DISK=disk-gcc.img、コマンド窓の命令数+FNVを指紋化) を作って
JIT on/offを比べたら、on側が**virtio記述子域の破壊→完了割り込み喪失→
デッドハルト**で死んだ。正体は正しさの穴:

- **page_has_code はインタプリタのfillしか立てていなかった** — JITだけが
  実行するページは自己書き換え/DMA上書きの検出網の外。ブート課程は混合実行が
  偶然ページを守っていた (jbootのビット同一が3日通っても見えない穴だった)
- 修正はbake時に「fillと同じ義務」でビットを立てる1行。再発防止テストは
  **全opがJIT語彙のSMCループ** (jit-a64/tests/smc_jit.rs) — 8bitストア版だと
  語彙外でインタプリタに落ちてfillがページを守り偽緑になる、まで込みで文書化
- 教訓: **門番はコースの数だけ強くなる**。jbootの指紋が緑でも、それは
  「そのコースで踏む経路」の証明でしかない。jcmdが2本目の指紋になった

修正後: gcc課程もon/offで**窓命令数518,000,000・FNV完全一致**。性能は
窓カバレッジ49.7% (ブート34%より上がる — 定常WLの読みどおり) だが
**まだ赤字**: off 54.6 MIPS vs on 48.6 MIPS。窓内の平均ブロックは1.8命令
(cc1は分岐+8bit演算が密で語彙外に当たりまくる)。次: 8bit語彙・入場税

## 2026-08-17: wasm JITの+19s事件 — 「instantiate地獄」は実在した (Nで来る)

ブラウザ実測でJIT onがブート2倍遅 (39.7s vs 20.2s)。税を分解 (diagモード:
probe-only/焼きまで/全部) したらプローブ・焼き・実行は各+数%で、残りの
大物は**据え付け = WebAssembly.Moduleのコンパイル固定費 ~0.5ms × 36,255個**。
jit-probe (F1a) の「instantiate 6.3µs」は1個の数字で、Nで来ると別の敵になる
— v86が多数ブロックを1モジュールに束ねている理由を自分の足で踏んだ。

対処: **バッチ据え付け** — bakeは本体 (code section body) だけ焼いて貯め、
pump時に最大4096本を1モジュール ("b0".."bN"のNエクスポート) に包んで
1回のinstantiate + table.grow(N) + 一括set。36kブロックが~15モジュールに。

結果 (node、熱ダレ帯): interp 46.4s vs jit 46.1s = **互角まで回復**
(バッチ化前は+28%)。決定性はビット同一のまま。ゲストのtime (仮想時計=TSC)
がon/offで2.25sピタリ一致するのは決定性の見せ場 — 「体感3分なのに結果が
速い」の正体は仮想時計と壁時計の区別である (ユーザー実測が教材になった)

## 2026-08-16: バッチ据え付けの検収 — ブラウザ実測でon/off差は+19s→+3s台へ

ユーザー不在のためClaudeが代測。2つの定規で交互A/B:

- **node (プロセス分離、ChromeのV8と同じエンジン)**: off/on交互3周で

  熱ダレ帯でoff床自体が50→61sまで漂流しているので差だけ読む
- **内蔵ブラウザペイン (既知の~3x減速環境、相対比較のみ有効)**: 起動秒ゲージで

## 2026-08-17: F1d-f — 8bit語彙で「cc1の主食」を取りに行った

IRの8bit形 (F1c-b2でV2に足したままエミッタ未実装だった分) を全部
AArch64エミッタに実装し、書く形 (Store8/Rmw8) はcoreに jit_try_write8 /
jit_try_rmw8 を足して原本委譲で追加。要点:

- **reg8はバイト番地の直アクセス** (LE前提: AL=regs[0]の第0バイト、
  AH=第1バイト) — bfi/ubfxの出番はなかった。ldrbのゼロ拡張がalu8の
  `a as u32` と同じ形になるのも都合がよい
- **cc_rは幅でマスクして控える** (alu_lazyの `& mask` の写し)。32bit形は
  u32の折り返しが勝手にマスクするので気づかない罠 — 8bitは `and w13,w13,0xff`
  を書かないと材料がビット同一にならない
- NEGのCF上書きだけ遅延材料に畳めない → grp3b8_reg をcore側に置いて
  ヘルパ1呼び (意味論の原本はcoreの中に留める)

授業料と対処が2つ:

1. **語彙を広げると衝突再焼きの嵐が来る**。JSLOTS 256Kのままだと焼き359k回
   (据付76kの4.7倍) で gcc窓 44 MIPS まで沈んだ。2Mへ広げて129k回・58 MIPSに
   回復 — 「焼ける頭が増える最適化」はスロット表の再設計とセット
2. **損益のローリング再審**: ブロックごとに入場/実行命令数を数え、256入場ごと
   に平均<3命令なら負の印に降格。一度きりの審査ではダメ (ブート期に良平均で
   通ったブロックが定常WLの分岐早退で走り続ける)。ブート入場74.8M→53.4M回

判定 (交互3周、off/on-main/on-f1d-fの3すくみ):

- **ブート**: off 9.9-11.1s / on-main 11.8-12.6s / on-f1d-f 10.6-10.9s —
  **初の互角** (3周目はoffに勝った)。F1d-e時点の+6%赤は消えた
- **gcc窓**: off ~67.5 / on-main ~47 (-30%) / on-f1d-f ~57 MIPS (-15%) —
  **赤字半減**。窓内入場34M回・平均7.8命令/入場 = 入場税は健全化した

残る-15%の正体は生成コードの実行密度: 毎opでゲストレジスタをロード/ストア
し、ALUごとにcc材料6ストア、Jccごとにh_condヘルパ呼び。インタプリタの
1命令あたりコストに構造で負けている区間が残る。次の手はレジスタ/ccの
ホストレジスタ常駐化 (ブロック内で生かす) — 骨格の「毎opロード/ストア」
前提を外す設計判断なので、着手前にADRで裁く。指紋2コースはビット同一のまま

## 2026-08-17: F1d-f2 — センサスが的を教え、ブートが初の黒字になった

**collectを止めたuopの度数** (opstats、bake時計上 — 実行時間を汚さない) を
core jit.rsに足し、jcmdの観測口に窓のオペコード差分と合わせて出した。結果:

- grp5 38% (間接call/jmp・push rm・inc rm) / mov moffs 27% / test [mem],imm 20%
  (grp3の0/1) / setcc 8% — この4系で9割を超える
- moffsは**新opなしで取れた** (base/index無しのJitMemに畳んで既存のMovRM/
  StoreMR等へ変換するだけ)。設計の貯金が効いた形
- 従来経路 (非dcache) は窓の4%だけ: movsx/cmov/MMX/imul imm/string系 +
  dcacheデコーダにB0-B7 (mov r8,imm8) が無い — JIT以前の穴として台帳へ

実装: setcc (r8/[m8] — h_cond既設なので条件→ストアだけ)・test imm 3形・
inc/dec [mem] (jit_try_incdec32、CF不変はinc_dec_w委譲)・push [mem]・
**間接分岐終端** (jmp/call r/m32 — 着地は既存のexit_abs。callは的を先に
読んでからpush = call esp系の意味を守る)。指紋2コースはビット同一のまま。

判定 (冷間・交互):

- **jboot: off 8.8s vs on 8.2s — JIT初の明確な黒字 (-7%、2周とも同値)**。
  970M/8.2s = 118 MIPS。インタプリタ100 MIPSの壁をJITが初めて越えた
- gcc窓: off ~74.8 vs on ~64.6 (-14%)。**f1とf2は同着** (65.5/63.7・64.6/64.9・
  60.9/59.7) — カバレッジ51→58.5%・平均8.5命令/入場に上がっても壁時計は不変

f2が窓で効かない理由はf1の診断の続き: 増えた限界命令の生成コードが
ヘルパ濃度でインタプリタと同速。**カバレッジはもう天井ではない — 密度が敵**。
f2の語彙は中立コストの布石として残す (密度が上がった日に丸ごと効く)。
次 (F1d-g): レジスタ/cc材料のホストレジスタ常駐化 — 骨格の「毎opロード/
ストア」前提を外す設計判断なので、ADRで裁いてから

## 2026-08-17: F1d-g — 密度の2梃子で、gcc窓ほぼ互角・全体ではJITが最速に

ADR-0023。実行時の新しい状態を持たない**エミット時の局所解析**だけで密度を上げた:

1. **g1: cc死储の省略** — 次opが観測されうる前にccを完全上書きする純レジスタ
   opなら、材料6ストアを書かない (xor-zeroing→testの類)
2. **g2: 条件判定のインライン化** — cc設定opの直後のJcc/setccは、材料が
   w10/w11/w13に生きている間にホストフラグ (`adds`/`cmp`/`cmp r,0`) + `cset`
   で判定。h_condヘルパ呼び (Jccは約1/7命令) が消える。ADC/SBB・P/NP・
   ADDのBE/Aは写像なし → 従来どおりh_cond

授業料1つ: **ADDのキャリーはARMのCと同極性で、subs系 (借り=!C) と逆**。
初版はcc2 (B) をloに写して即死 — 全数照合テスト (tests/cond_inline.rs、
全kind×全16cc×両幅×境界値でJIT on/offのsetcc値+6フラグを突き合わせ) が
一発で暴いた。「意味論の二重実装に半歩踏み込むなら、守りは全数照合」の実証。
もう1つの地雷 (8bitの桁): `lsl 24` で上位バイトに寄せてからadds/cmpすると
C/V/N/Zの桁が8bit演算と一致する。

判定 (冷間・交互3周、off / on-main(f2) / on-g):

- **jboot**: off ~9.5s / on-f ~8.8s / **on-g 8.1-8.2s (全周勝ち、-14%、119 MIPS)**。
  ばらつきも最小 (8.1/8.2/8.2)
- **gcc窓**: off ~82.5 / on-f ~78.2 (-5%) / **on-g ~80.6 MIPS (-2.3%)** — 各周で
  fに勝ち。**起動込み全体では on-g 21.7-22.3s vs off 23.5-25.0s = JITが最速**

指紋2コースビット同一のまま。残る窓の-2%は毎opのゲストレジスタロード/
ストア (レジスタ常駐化はADR-0023で保留 — ヘルパ境界のflush規律が大工事)。
次の一手はこの台帳を見て決める

## 2026-08-17: 広範囲調査 第2ラウンド — プロファイル・サーベイ・入場路の痩身

3本立ての調査 (台帳は [jit-roadmap2.md](jit-roadmap2.md)):

1. **sampleプロファイル実測**: JIT onの時間内訳は インタプリタ37-48% /
   生成コード14-20% / 入場機構8% (try_enter 6.3-6.5 + TLSのtlv呼び1.5-2.0) /
   ヘルパ群10-13% / bake系4-5%。静的見積では**1入場≈90-100ホスト命令**の固定費
2. **外部サーベイ** (QEMU/Rosetta 2/FEX/Box64/v86/Dolphin): 決定性と両立して
   効きそうな順は (1) TB chaining (QEMUはicount同居の実績あり)、(2) 間接分岐
   キャッシュ、(3) guest→hostレジスタ固定写像 (Rosettaの土台)、(4) ストアTLB
   インライン、(5) NZCV直写像 (FEX +17.6%)。Rosettaが「最適化パス無し1:1変換」
   でネイティブ比7-8割という事実はテンプレートJIT路線の強い裏付け
3. **F1d-h: 入場路の痩身バッチ** (実装・マージ対象): entry引数化 (mov_abs×3→
   mov×3)・出口ip番地のx19相対化・**ヘルパ表x22** (mov_abs→ldr、26箇所)・
   **TLS排除** (JitHook.ctx — macOSのtlv呼びを入場路から追放)・**Slot 16B化**
   (BlockをBoxへ — 2Mスロット表128MiB→32MiB)。
   判定: gcc窓交互4周 (熱ダレ1周除外) で **+0〜2%の微益〜中立**。期待値
   0.2-0.3s/8sの削減は単体ではノイズ床 (±3%) と同格 — 構造根拠+メモリ削減で
   採用。指紋2コースビット同一・全テスト緑

結論: **次の主砲はTB chaining (F1d-i)**。入場機構8%+清算+出入り26命令×
53M回が的で、期待10-15%級。予算の契約 (ブロック頭の自前予算検査+レジスタ
持ち回り) と世代でのリンク剥がしが設計の本体 — ADRで裁いてから

## 2026-08-18: F1d-i TB chaining — 作って測って「不採用」、そして本物の梃子が見つかった

ADR-0024の契約どおり実装した: 後方直接分岐 (ループ) の出口をパッチして次
ブロックの本体へ直接飛ぶ。予算w23/積算w24のレジスタ持ち回り・スタブの
プレースホルダ焼き+imm畑のリンク時書き換え・剥がし台帳 (退去/降格/世代落ちの
全経路でmprotect+icache無効化のアンパッチ)。**指紋2コースはビット同一一発**
— 決定性の契約 (ADR-0024) は設計どおり成立した。

観測: ブート入場53.1M→42.3M回 (-20%)・平均7.9→10.1命令/入場、gcc窓
結線12.5k・剥がし792 (退去時の生存契約が実地で回った)。

**しかし壁時計は動かない**: 窓 交互3周でmain比-1%〜同着、ブート同着。
入場が2割減っても時間にならない理由を掘って、構造の天井に当たった:

- **予算 = min(鎖残り, tick_countdown) で tick粒度が64命令** — チェーンは
  最長でも数ブロックで必ず表口に戻る。F1d-hで入場固定費は既に~70命令まで
  痩せており、64命令ごとの往復1回は消せない税ではなかった
- QEMUのTB chainingが主砲なのは icount粒度が桁違いに大きいから。教訓:
  **他所の主砲は、自分の税表で答え合わせしてから撃つ**

**診断実験 (マージしない)**: INSTRUCTIONS_PER_TICK 64→256にすると —
- gcc窓: off 85.8 / on **90.7 MIPS (JITがoffに勝つ、+5.7%)**、
  起動込み全体 **22.0→17.7s (-20%)**。on/off指紋は新粒度内で完全一致
- chaining有無はtick=256でも同着 → 利得は粒度そのもの (往復が1/4)

つまり**次の本物の梃子はtick粒度**。ただしこれはゲスト可視のタイミング変更
(割り込みレイテンシ・PIT/シリアルの刻み・**ネットワークRTTは刻みで決まる**
[2026-08-15の実測]・golden/指紋の基準値が全部変わる) — 性能最適化ではなく
**意味論の基線変更**なので、ユーザーの裁定事項。台帳に置く。

chaining実装はタグ exp/f1d-i-chaining に寝かせる (粒度が変わる日が
来たら再訪 — その時はtick=256でも同着だった事実も思い出すこと:
**粒度を上げるとchaining自体も要らなくなる**可能性が高い)

## 2026-08-18: tick=256 (ADR-0025) — JITが全定規で勝ち、F1d (JIT編) を締める

ユーザー裁定で採用。要点は **PIT_CLOCKS_PER_TICK も4に比例させて
「1命令≒10ns」の換算を不変に保つ**こと — 粒度だけ256にした初手は
ゲスト時計が命令比1/4に遅くなり、benchカーネルがデッドハルトした
(時間の換算とまとめ幅は別の量、という授業料)。比を保ったら:

- **凍結benchブートは970,000,000命令ちょうどのまま** (定規は無傷)。
  シリアルFNVだけ張り替え (µsタイムスタンプの配送ジッタ) — 門番は
  on/off相対なので新値でもビット同一
- **jboot: on 7.3s = 133 MIPS** (off 8.8s、-17%)
- **gcc窓: off ~78-80 vs on ~82-83 MIPS — JITが窓でも勝った** (交互3周全勝)。
  起動+コンパイル全体 24.6-25.2 → 20.4-20.6s (**-17%**)
- **RTT (netlat)**: 悪化なし〜改善 (10M: 88.3→88.6ms同 / 1M: 37.4→28.6 /
  100k: 16.1→10.2 / 16bit完全同一)。RTTの主因は刻み (壁時計) — 換算を
  保てば揺らがない
- テスト204本緑 (ゲスト時間ハードコードの2本は「命令/PITクロック比」に書換)

**F1d (JIT編) はここで一区切り**: a骨格→b/cメモリ語彙→d TLBインライン→
e 定規と正しさ穴→f 8bit語彙+損益再審→g 密度 (条件インライン)→h 入場路痩身→
i chaining (不採用の学び) → tick=256。最終形: **ブート133 MIPS・gcc窓でも
JIT優位・決定性ビット同一・門番4種 (jboot/jcmd/jit-check/cond_inline)**。
残り玉は台帳 (jit-roadmap2.md): レジスタ固定写像・間接分岐キャッシュ・
ストアTLBインライン・wasmへのg1/g2還流

## 2026-08-18: wasm還流 (g1/g2) — 正しさ緑・性能同着、wasmの敵は別に居る

ユーザーのブラウザ実測「起動はJIT OFFが速い・gccは変わらない」を受けて、
ネイティブのg1 (cc死储省略)・g2 (条件インライン) をwasm生成器へ還流した。
coreは無傷 — wasm/src/jit.rsだけ。

- wasmにはホストフラグが無いので、g2は材料 (L_A/L_B/L_Rローカル) からの
  **wasm式** (i32.lt_u / le_s / eqz / xor-and-shr…) で条件を直接計算し、
  cond importの呼びを消す。ARMで諦めたADDのBE/A (CF|ZF) も式1つで書けた。
  P/NPとADC/SBBは従来どおりimport

## 2026-08-18: fastmem 段2 — 作って測って「CR3の壁」に当たった (未マージ)

線形ミラーを有効表方式 (フォルトさせない — 1バイト/ページの検査+直読み) で

立つ) で群判定。JITのemit_loadに全幅・CPL3対応のミラー路。

- **正しさは緑**: fastmem×JITの4通りで指紋完全一致 (jboot 8810…/jcmd dc43…)
- **性能は赤 (-10%)**: 窓70-73 MIPS (基準78-82)。観測が原因を指した —

  全無効化はx86の意味論どおりで、ミラーが温まる前に消える。しかも
  外れ側でも検査の前置き (~12命令) を払う

**次の一手はPGE (グローバルページ)**: PTE.G + CR4.PGEはCR3書き込みを

テキスト) をGで張る。CPUIDでPGE (bit13) を名乗ればカーネル半分のミラーが
プロセス切替を跨いで生きる。ただし**CPUID広告はゲスト可視の基線変更**
(カーネルがGビットを使い始める → 指紋張り替え第3弾) — ユーザー裁定待ち。
広告した場合の実装義務: CR4.PGEトグルで全剥がし・invlpgはG含め剥がす
(どちらも既存フックの延長)。ソフトTLB側もG保持すれば追加の利得

代替案も台帳へ: ページテーブル書き込み追跡 (walkerが踏んだ表ページを
note_write網で見張る — Dolphin PR #13768の完全形、重い) / Linuxホスト
(4KiBページ) なら群制約が消えるがmacOSが主定規 (ユーザー裁定でWSL2計測は省略)
