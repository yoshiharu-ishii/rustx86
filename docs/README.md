# rustx86 のドキュメント — 現代PCの成り立ちを辿る

このプロジェクトは「x86エミュレータを作る」と同時に、
**現代のPCがなぜこの形をしているのか**を辿る教材でもある。

PCは40年分の後方互換が地層になってできている。今のCPUも電源投入直後は
1978年の8086として起動し、そこから32bit、64bitへと自分で自分を昇格させていく。
その地層を下から順に自分の手で作り直すと、普段ブラックボックスとして
扱っているものが繋がって見えてくる。

## 読む順番

### 1. まず全体像を掴む

**[アーキテクチャ](architecture.md)** — CPUと装置の接続図、16bitと32bitの違い、
アドレス変換の三段跳び。図中心なので、ここから読むと迷わない。

扱っている問い:

- なぜブートセクタは 0x7C00 という半端な番地に置かれるのか
- なぜセグメントは16倍されるのか
- 割り込みベクタテーブルを「OSが乗っ取る」とはどういうことか
- なぜ1981年のタイマーチップ (8254 PIT) が現代のPCにも生きているのか
- 32bit化は本当に「命令が増える」ことなのか
- なぜブラウザからは ping が打てないのか

### 2. ビルドの中身を知る

**[ビルドの最小構成](build.md)** — Rust の入れ方から、wasm-pack が何を生成して
いるか、`--target web` を選んだ理由、wasm特有の落とし穴まで。

扱っている問い:

- `wasm32-unknown-unknown` の「OS無し」は何を意味するのか
- wasm 単体では文字列すら渡せないのに、なぜ `String` が返せるのか
- なぜ `python3 -m http.server` を使わないのか
- wasm のメモリが伸びると、JS の `Uint8Array` に何が起きるのか

### 3. なぜそう作ったかを知る (ADR)

設計の決定と、その理由・代償を記録したもの。
決めた時点の情報で書いてあるので、後から読むと判断の過程が追える。

- **[ADR-0001: 16bit CPUから始め、Unicornをオラクルに検証する](adr/0001-16bit-cpu-and-cosim.md)**
  — なぜリアルモードから始めるのか。x86には網羅テストROMが無いという問題に
  どう立ち向かうか。「緑のテストは何も証明しない」という実測付きの教訓

- **[ADR-0002: CPU以外の装置を作り、16bit UNIX (ELKS) を起動する](adr/0002-devices-and-16bit-unix.md)**
  — CPU単体には意味がない。次に何を動かすか。FreeDOS / ELKS / Linux の比較と、
  「その作業は最終目標でも生きるか」という判断軸

- **[ADR-0003: ブラウザ内でネットワークをどこまで本物にするか](adr/0003-networking-in-the-browser.md)**
  — ブラウザは生パケットもICMPも出せない。それでも `dig` と `ping` を
  サーバー無しで動かす方法と、どこから踏み台が必要になるかの線引き。
  踏み台を公開しないと決めた理由 (宛先を隠してしまう装置になる)。
  「ゲストのLinuxはスタックをどこまで支配できるか」を測るための
  L2ブリッジ構成 (個人実験。踏み台は本リポジトリに含めない)

- **[ADR-0004: BIOSにどこまで付き合うか](adr/0004-how-far-to-follow-the-bios.md)**
  — 相手を増やすたびにBIOSを実装し続ける羽目にならないか。**需要が有界な相手と
  無界な相手がいる**。OS本体は有界、DOSアプリは無限、そして32bit Linuxは
  ブート方式の選択によって**構造上ゼロ**になる。
  実際にFreeDOSを動かした結果 (穴は5個で足りた。**止まったのはBIOSではなくCPUだった**) も追記済み

- **[ADR-0005: ローカルで完結するものを先にやる](adr/0005-local-first-roadmap.md)**
  — ネットワークを最後に回した判断。**「先に書くと無駄」と「無駄」は違う**。
  16bit時代にNE2000を書くと Linux に着いた時点で置き換えになるが、
  踏み台とvirtio-netが揃った後なら装置を1つ足すだけで済む

## この教材の立ち位置

エミュレータの解説は「命令セットの実装方法」に寄りがちだが、
実際に難しいのは**命令ではなく機構**である。割り込み、特権、アドレス変換、
装置との協調 — この辺りは仕様書を読んでも掴みづらく、
動くものを作ると腑に落ちる。

そこで本プロジェクトでは、各段階で**必ず何かが動く**ように目標を置いている。
「CPUは完成したが動かすものがない」という状態を作らないのが方針である。

**段の一覧はここに書かない** — [ロードマップ](../README.md#ロードマップ) が本体で、
二重に持つとズレる (実際ここの表は順序が変わったまま古くなっていた)。
深さの **Tier** と、広さの **箱 (B)** の2軸で並べてある。

64bit (ロングモード) はこのリポジトリでは扱わない。やるなら fork して
別リポジトリにする — **終わりを持たせるための線引き**である。
